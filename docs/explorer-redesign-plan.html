Explorer Tab Redesign

A user-friendly redesign of the file browser for raw/, wiki/, and outputs/ — grounded in the current codebase, the data the backend already exposes, and standard file-manager UX patterns.

1Executive summary

The Explorer's job is simple: let a user find, read, and occasionally delete files across the three knowledge-base buckets. Today it does that, but clumsily. This plan keeps the existing three-tab mental model and the existing backend APIs, and rebuilds the surface around a master–detail split, real metadata, soft-delete with undo, and keyboard-first navigation.

The single biggest win is replacing the stacked "list-then-preview-below" layout — where selecting a file collapses the list to a ~3-row sliver — with a persistent two-column split. The second is surfacing data the backend already returns but the UI throws away: file paths for nested raw files, wiki word counts and outbound links, and the entire trash system.

Scope discipline. This plan is deliberately conservative. It reuses api.listFiles, api.getFile, api.deleteFile, api.listTrash, api.restoreTrash, api.emptyTrash, and api.promote exactly as defined today. Only one small, optional backend change is proposed (exposing wiki-index metadata in the files payload) — and even that has a frontend-only fallback.

Priority labels used below:

Must = ships in phase 1   Should = phase 2   Nice = phase 3 / deferred   Backend = requires a backend change

2What's wrong today

Concrete problems found by reading ExplorerTab.tsx against the data the backend actually returns.

Layout & space

  • The file list is capped at max-h-48 (~3 visible rows) and the preview panel renders below it. Selecting a file means you can no longer see the list while reading — you lose your place.
  • The three category tabs are flat lowercase text with bare counts. There's no visual distinction of the active tab beyond a blue underline, and the count is the only signal of what's inside.
  • No breadcrumb or heading. Once you're in raw/ with nested folders, the panel gives no indication of where you are.

Information that's available but hidden

  • rel already includes the subdirectory path for nested raw files, but the table only renders file.name — so emails/2024/foo.txt and handbooks-and-guides/foo.txt look identical.
  • kb/index/wiki_index.json carries title, links_to[], and words for every wiki page. The UI uses none of it beyond the title.
  • The backend exposes a full trash API (listTrash, restoreTrash, emptyTrash) and api.ts already wraps it — but there is zero UI for it. Deletes look permanent.
  • The promote action (outputs → raw) exists and is wired in AskTab, but is unreachable from Explorer when viewing an output.

Interaction & safety

  • Delete is a raw confirm() dialog triggered by tiny red "Delete" text inside a clickable row. One stray click on the row and you're in the dialog; one stray click on the text and a file is gone. No undo, no trash visibility.
  • No keyboard navigation: no arrow keys to move between rows, no Enter to open, no Escape to close the preview, no / to focus search.
  • Filter matches only name and title — not file contents. For a knowledge base, "find the page that mentions X" is the most common search, and it isn't supported.
  • Sort is a separate dropdown with fixed options. The table headers are not sortable, even though Size and Modified are right there.
  • Preview silently truncates at 100,000 characters with a plain (truncated) suffix — no indicator of how much was cut, no "show full" affordance.

Polish gaps

  • No file-type affordance — no icon, no colored badge, no extension chip. A .pdf, a .md, and a .txt look the same.
  • Empty states are passive text. "No source files yet" doesn't offer a button to the Ingest tab, even though the app knows exactly where to send you.
  • "Download HTML" only appears for wiki/.md. Raw markdown and outputs can't be downloaded at all from Explorer.
  • No URL state — you can't link to or bookmark a specific file.
  • Internal wiki links render with a strike-through if the target isn't in the current category's file list (the lookup is active.files.find(...)), so a wiki link to a page that exists in wiki/ shows as broken when you're browsing raw/.

3Goals & principles

The redesign is judged against these. If a proposed feature doesn't serve one of these, it gets cut.

  1. Find first. The Explorer is primarily a search-and-read tool. Finding the right file should be sub-second; reading it should be comfortable.
  2. Master–detail, persistent. The list and the reader stay visible together. Selecting a file never hides the list.
  3. Don't surprise, don't destroy. Deletes are soft, reversible, and confirmed with a clear undo affordance — never a bare confirm().
  4. Show what the system knows. If the backend returns metadata (paths, word counts, link targets, trash state), the UI should use it rather than discard it.
  5. Keyboard-first, mouse-complete. Every frequent action has a key. The mouse path is never the only path.
  6. Match the app, not the web. This is a desktop-style tool inside a Next.js app. Use app conventions (Sidebar, SectionCard, ActionButton, slate/blue palette) — don't import a generic file-manager chrome.
  7. Surgical. Reuse existing APIs and shared components. No new dependencies. No backend rewrites unless a phase explicitly calls for one.

4Proposed layout

A persistent two-column master–detail, with a slim command bar on top. The three categories become a segmented control in the bar, not full-width tabs.

┌──────────────────────────────────────────────────────────────────────────┐ │ [ Wiki 42 ][ Raw 117 ][ Outputs 9 ][ Trash 3 ] 🔎 Filter… ⟳ Refresh │ ├──────────────────────────────────────────────────────────────────────────┤ │ ╭────────────────────────╮ ╭───────────────────────────────────────────╮ │ │ │ Master (file list) │ │ Detail / Reader │ │ │ │ │ │ │ │ │ │ ▸ 📁 emails │ │ Data Quality Assessment Framework │ │ │ │ 📄 note-2024-03.txt │ │ wiki/data-quality-….md · 1,640 words │ │ │ │ ● handbooks-and-guides │ │ [Download] [Copy] [Promote] [Delete] │ │ │ │ 📄 onboarding.md │ │ ────────────────────────────────────────── │ │ │ │ … │ │ │ │ │ │ │ │ │ │ │ │ 42 files · sorted A→Z │ │ │ │ │ ╰────────────────────────╯ ╰───────────────────────────────────────────╯ │ └──────────────────────────────────────────────────────────────────────────┘

Layout rules

  • Command bar (sticky, top): segmented category control with live counts, a filter input (with / shortcut), a sort control, and Refresh. The Trash count is a chip-button that opens the Trash drawer (see §8).
  • Master column (left, ~38% width, min 280px, max 420px): scrollable file list. Respects category, filter, sort, and folder grouping.
  • Detail column (right, fills remainder): the reader/preview. Persistent — clicking a file updates only this pane.
  • Responsive: below 720px width, the columns collapse to a single column with a "← Back to list" affordance in the detail header (the selection is preserved in state).
  • Nothing stacks vertically except on mobile. The list never shrinks below ~6 visible rows.

5The file list (master)

Replace the four-column table with a richer, grouped, virtualization-tolerant list. Keep it cheap — no new data fetching.

Row design Must

Each row is a button (semantic, keyboard-focusable) showing three lines of info from data the backend already returns:

📄 Data Quality Assessment Framework
data-quality-…md · 1.6 KB · 2026-05-12
1,640w
📄 qa-20260410-003833
outputs/qa-…md · 3.2 KB · 2026-04-10
  • Primary line: title || name (already done today; keep it).
  • Secondary line: the rel path (not just name), plus size_h and modified_h. This fixes the "nested raw files all look alike" bug.
  • Trailing chip (wiki only): word count from wiki_index.json. See §9.
  • Type glyph: a small monochrome glyph or colored extension badge (md / txt / pdf / json / …) derived from the filename. No icon-font dependency — a static map to an emoji or a 3-letter badge is enough.

Folder grouping for raw/ Should

Raw files live in subdirectories (emails/, handbooks-and-guides/, slide-decks/, …). Today they're flattened. Proposed: a collapsible group per top-level subdirectory, with a count badge; files at the root sit in an implicit "Ungrouped" group at the top.

▸ 📁 emails (14)
📄 note-2024-03.txt
emails/2024/…
▸ 📁 handbooks-and-guides (38)
▾ 📁 Ungrouped (3)
📄 Windows-11-25H2-….txt
2.1 KB

Group state (open/collapsed per folder) is local component state. The filter collapses all groups and shows flat matches; clearing the filter restores prior group state.

Sorting Must

  • Keep the existing sort keys (newest, oldest, name A→Z, name Z→A, largest) in a control — but move it to a compact Sort: Newest ▾ dropdown in the command bar.
  • Default sort: Modified, newest first for outputs and raw; Name A→Z for wiki (an alphabetical wiki is more browsable than a chronological one).
  • Folder groups always sort internally by the chosen sort; the groups themselves sort by newest member (or alphabetically when the inner sort is name-based).

Selection & focus

  • Single selection (today's model). Clicking a row selects it and loads the detail pane.
  • The selected row gets a left accent border + soft fill, exactly like today's bg-blue-100.
  • Keyboard: ↑/↓ move focus between rows, Enter opens, Esc returns focus to the filter. Detail pane updates on focus-move when Enter is pressed; arrow-move only previews on hover- equivalent (configurable: "preview on hover" off by default to avoid content flashing).

6The detail / preview pane

A reader-first panel that stays put while the list scrolls beside it. Header carries identity + actions; body carries rendered content.

Header Must

  • Title (large, truncate with tooltip): title || name.
  • Subtitle line: full rel path, word count (wiki), size, and modified date — the metadata that today is crammed into a tiny size_h | modified_h string.
  • Action toolbar (right-aligned, wrapping on narrow widths): Download, Copy path, Copy content, and — conditionally — Promote (outputs) or Delete. Buttons use the existing slate/blue styles; Delete is the only red one and lives last.

Body Must

  • Markdown files (wiki, outputs, and .md in raw) render via the existing ReactMarkdown + remarkGfm pipeline. Keep the internal-link resolver from today, but fix the scope bug: resolve against the wiki file list always, regardless of which category is active, since wiki links point to wiki pages. Broken links get a tooltip and a muted style, but not a strike-through (strike reads as "deleted").
  • Other previewable text files render in a monospace <pre> with line-wrapping toggle (today's behavior, plus a wrap on/off control).
  • Binary / non-previewable files show a friendly empty state with the file type, size, and a "Download" button — not the current bare "Binary file — preview not available".

Truncation, done honestly Must

Replace the silent 100k slice with a visible truncation banner: "Showing first 100,000 of N characters — Download to view in full." Compute N from the fetched content length (note: today the API returns full content, so N is just content.length; the cap is a render-side guard, not a server limit).

Empty & loading states Must

  • Nothing selected: a centered placeholder with an icon and "Select a file to preview" — plus, for empty categories, the actionable empty state below.
  • Loading: a skeleton in the detail body (today's "Loading preview…" text is fine but should sit inside the body, not replace the header).
  • Empty category: today's hint text, but rendered as a call-to-action card with a button that switches the sidebar view — raw → "Open Ingest", wiki → "Open Compile", outputs → "Open Ask". This requires the tab's onNavigate, threaded in via a prop (see §10).

7Trash & undelete Must

The backend and api.ts already support soft-delete, list, restore, and empty. The Explorer is the natural home for it. This closes the biggest safety gap.

Delete UX

  • Replace the inline confirm() with an inline confirm popover anchored to the Delete button: "Move name to trash? [Undo available for 5s]". Two buttons: Delete (red) and Cancel. No native dialog.
  • After delete, show a toast (bottom-right, app-style) with Undo for 5 seconds. Undo calls api.restoreTrash(name, category) immediately — no need to open the Trash drawer. This is the single most important safety improvement.
  • Row delete button only appears on hover/focus of the row (not always visible), reducing mis-clicks. It stays always-visible on touch devices.

Trash drawer

The command-bar "Trash (N)" chip opens a right-side drawer (or a modal on mobile) listing TrashItem[] from api.listTrash(). Each row shows:

  • Original name + category badge + trashed-at timestamp.
  • Restore (per-item) → api.restoreTrash(name, category).
  • Empty all (per-category or all) → api.emptyTrash(category?), behind a second inline-confirm.
  • The drawer refreshes its own list on open; restore/empty update it locally.
Conflict handling. restore_from_trash raises FileExistsError (HTTP 409) if a file with the original name now exists. The UI must surface that as a clear "A file with this name already exists — rename or delete the current one first" message, not a generic error. The backend already returns ALREADY_EXISTS; just map it.

8Search & filter

Today: name+title substring match. That's a reasonable baseline; the plan extends it without a backend rewrite.

Filter (instant, client-side) Must

  • Keep the existing name+title substring match as the default — it's fast and needs no new data.
  • Add a path-aware match: also match against rel (so emails finds all files under emails/).
  • Show a live result count in the filter bar: "3 of 42 match". Clearing the filter restores full list.
  • Esc in the filter clears it; / anywhere focuses it.

Content search Nice Backend

A true full-text search across file bodies would need a new endpoint (/api/search?q=…) that greps the three directories and returns matches with snippets. This is valuable for a knowledge base but is a separate feature with its own scope (snippet highlighting, regex, scope-by-category). It is out of scope for this redesign and listed only to bound expectations. The FAISS-backed Ask flow is the app's real semantic search; Explorer's filter should stay lexical and instant.

Filter chips / facets Nice

Optional, phase 3: quick-filter chips by extension or by folder, generated from the current list. Cheap to build from in-memory data; useful when raw/ grows large. Skip for now if the lists stay under a few hundred items.

9Wiki-specific richness

The wiki category has metadata the others don't. Use it to make the wiki browsable like a wiki, not just a file list.

Word count + outbound links Should

kb/index/wiki_index.json maps each page to {title, links_to[], words}. Two ways to surface it, in order of preference:

  1. Backend Preferred: extend /api/files/wiki to merge words and links_to into each FileMeta (the handler already loads wiki_index.json for titles — adding two more fields is a 3-line change). Frontend reads them from file directly.
  2. Frontend-only fallback: fetch /api/files/wiki as today, and separately fetch the index JSON. The index isn't currently served at an HTTP endpoint, so this actually still needs a tiny backend route — making option 1 strictly better. Go with option 1.

Where it shows up:

  • List row trailing chip: 1,640w (word count).
  • Detail header subtitle: · 1,640 words · links to 3 pages.
  • Detail sidebar (collapsible, right edge): "Outbound links" list — clicking one navigates to that wiki page within Explorer (re-resolve via the wiki list). Broken links show muted with a tooltip.

Internal link resolution — bug fix Must

Today's resolver does active.files.find((f) => f.name === targetName), where active is the currently-selected category. A wiki link clicked while browsing outputs or raw will always look up against the wrong list and render as broken. Fix: resolve against the wiki file list specifically (a cheap second useFileList("wiki") call, or a shared lookup). If the target exists, clicking switches to the wiki tab and selects the page; if not, render muted with a tooltip — no strike-through.

INDEX.md affordance Nice

wiki/INDEX.md is auto-generated. Consider pinning it to the top of the wiki list with a small "index" badge so it's discoverable as the entry point. Low value, low cost.

11Accessibility

The current table has no roles, no keyboard focus, and the delete "button" is nested inside a clickable row. Fix these.

  • The master list is a <ul role="listbox"> of <li role="option"> buttons, not a <table>. (The table semantics never fit a file browser.)
  • Active selection tracked via aria-activedescendant on the listbox so screen readers announce the focused file.
  • Delete is a real <button> with aria-label, not a clickable <td>. The inline confirm popover uses role="dialog" and traps focus while open.
  • Toasts are role="status" aria-live="polite; Undo toasts are aria-live="assertive".
  • Color is never the only signal: selected row has both the blue accent and a left border and an icon. Type badges use text labels, not color alone.
  • Maintain the app's existing light/slate palette and contrast — no new dark mode in this phase.

12Data & backend notes

What changes, if anything, server-side. The plan is engineered to need almost nothing.

Used as-is (no change)

  • GET /api/files/{category} — already returns name, size, size_h, modified, modified_h, rel, title?. The redesign uses rel properly.
  • GET /api/file/{category}/{path} — content fetch unchanged.
  • DELETE /api/file/{category}/{path} — soft-delete already moves to trash.
  • GET /api/trash, POST /api/trash/restore, DELETE /api/trash — wired in api.ts, just need UI.
  • POST /api/promote — exists, used in AskTab; reuse for outputs.

One small, optional backend change Backend

In list_files (the wiki branch), the handler already loads wiki_index.json for titles. Extend the merged meta dict to also include words and links_to from the same entry:

# inside the wiki branch, where titles[fname] = entry["title"]
if isinstance(entry, dict):
    titles[fname] = entry.get("title")
    meta.setdefault("wiki", {})  # or flatten:
    meta["words"] = entry.get("words")
    meta["links_to"] = entry.get("links_to", [])

And add words?: number and links_to?: string[] to the FileMeta TypeScript interface. Frontend treats both as optional so it never breaks if the index is missing.

Frontend-only fallback if the backend change is declined

Skip the word-count chip and outbound-links sidebar. The rest of the redesign ships without them. They're "Should", not "Must".

Client-side download for binary files

Today api.getFile returns previewable: false with no body for binaries. For the "Download original" action on binary files, fetch the raw bytes directly from a served static path or add a minimal GET /api/file/{category}/{path}?raw=1 that streams the file with Content-Disposition: attachment. Prefer the query-param route — it's a 5-line addition and avoids exposing raw filesystem paths. Backend Nice

13Implementation phases

Each phase is independently shippable and leaves the app usable at every step.

Phase 1 — Structure & safety Must

  1. Replace the stacked layout with the master–detail split (command bar + two columns; mobile collapse).
  2. Rebuild the master list as a role="listbox" of button rows showing rel, type badge, size, and modified; selected row styled with accent + border.
  3. Move sort to a compact dropdown in the command bar; keep existing keys; set category-specific defaults.
  4. Move Delete to hover/focus with an inline confirm popover; add the Undo toast wired to api.restoreTrash.
  5. Add the Trash chip + drawer (list, per-item restore, empty-all with confirm). Uses existing api.listTrash/restoreTrash/emptyTrash.
  6. Fix the internal-link resolver to look up against the wiki list regardless of active category; drop strike-through for broken links.
  7. Honest truncation banner replacing the silent 100k slice.
  8. Actionable empty states with navigation buttons to Ingest/Compile/Ask (thread onNavigate into ExplorerTab).
  9. Keyboard: /, Esc, ↑↓, Enter, 1–3.

Phase 2 — Richness Should

  1. Backend: merge words + links_to into wiki FileMeta (the one small change).
  2. Word-count chip on wiki rows; words + link count in detail subtitle.
  3. Outbound-links sidebar in the detail pane (wiki only), click-to-navigate.
  4. Folder grouping for raw/ with collapsible groups and counts.
  5. Detail toolbar: Download original, Copy content, Copy path, Promote (outputs).
  6. Filter result count ("3 of 42 match") + path-aware matching.
  7. Toast system promoted to app root; used by promote/copy/delete.

Phase 3 — Polish Nice

  1. URL state (?tab=&file=) with history.replaceState.
  2. Filter chips by extension/folder for large raw/ sets.
  3. Pin wiki/INDEX.md with an "index" badge.
  4. Optional binary download endpoint (?raw=1) and Download-original on non-previewable files.
  5. Line-wrap toggle for the code preview; remember preference in localStorage.
  6. Remember last-selected category and last sort per category in localStorage.

14Non-goals & open questions

Explicitly out of scope

  • Full-text/content search. The app's semantic search lives in the Ask tab via FAISS. Explorer filter stays lexical and instant. A grep endpoint is a separate feature.
  • Multi-file selection & bulk operations. Adds complexity (bulk delete, bulk promote) for a personal KB with modest file counts. Not worth it until there's a demonstrated need.
  • Rename / move / create. The KB's workflow is "raw in → wiki compiled → outputs generated". Manual file ops aren't part of it; the backend has no endpoints for them and we shouldn't add them here.
  • Drag-and-drop upload. Belongs to the Ingest tab, not Explorer.
  • Dark mode. The app is light/slate today; matching it is correct. A theme pass is a separate effort.
  • New dependencies. No virtualization library, no icon font, no toast library, no DnD kit. Everything above is doable with existing React + Tailwind.

Open questions for the maintainer

  • Should the Trash drawer live in the Explorer, or as a shared app-level control (e.g., in the Sidebar)? Explorer is the natural home, but the Sidebar already shows file counts and could host a trash badge.
  • For raw/ folder grouping, is "group by top-level subdirectory" sufficient, or do you want deeper nesting (e.g., emails/2024/)? Top-level is recommended first; deeper is a config knob later.
  • Is the one backend change (wiki words/links_to in the files payload) acceptable, or should phase 2 ship frontend-only and drop the wiki richness?
  • Should the Undo toast restore immediately on click, or queue the restore and run it on the next refresh? Immediate is simpler and matches user expectation; queueing is safer if restores are slow.
  • Outputs' qa-*.md files have timestamps in the filename — do you want a "group by date" view for outputs, or is the newest-first flat list enough?
